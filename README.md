# GameFPS · 游戏帧率实时监测

一套 Windows 平台的实时游戏帧率监测工具，参照「游戏加加」的监测主干实现：
**帧率 + 1% Low + 硬件占用 + 游戏内悬浮窗 + 实时曲线**。

采集全程 **不向游戏进程注入任何代码**，走 Windows 内核 ETW 事件（与 Intel PresentMon / CapFrameX 同一路线），
因此不存在被反作弊判定为外挂的风险。

> **本项目完全由 Vibe Coding 写成。**
> 从第一行代码到现在的每一个功能、每一次修复、每一版打包，全部是
> 「人提需求 → AI 写码 → 人装机验证 → 反馈现象 → AI 再修」这个循环跑出来的，
> 没有手工逐行编写的部分。README 里那些「为什么这样做」的段落，
> 也是在这一来一回里被追问出来的。
>
> 这意味着两件事：**一**，代码风格和注释密度带有明显的 AI 痕迹，抽象层次不总是最优，
> 个别地方存在过度设计；**二**，它的正确性来自反复的真机验证和日志取证，而不是来自
> 作者多年的 Windows 系统编程经验 —— 所以遇到问题时，日志比猜测有用得多。
>
> 另有两份长文就放在仓库根，动代码前值得先看一眼：
> [`开发文档.md`](开发文档.md) 逐模块讲清「怎么实现的、用哪些代码、为什么这样设计」，
> 附症状→根因排错地图、改动影响面速查与当前已知缺陷清单；
> [`开发日志.md`](开发日志.md) 从 v1.0.0 到 v1.0.36 每个版本记一条
> 「需求原话 → 修了什么 → 怎么修的 → 为什么这样修」。

不想编译的话，去 **[Releases](https://github.com/awa48666/game-fps-monitor/releases/latest)** 下载：


## 从源码构建

需要 .NET 10 SDK、Node.js 与 pnpm。

```powershell
# 备份并安装前端依赖
cd app
npm install          # 或 pnpm install

# 打包（默认自包含：产物形状与 GitHub Release 一致）
cd ..
.\publish.ps1

# 只为本机快速验证，愿意接受目标机需自带 .NET 10 桌面运行时
.\publish.ps1 -FrameworkDependent

# 产物在 dist\GameFPS\，双击 GameFPS.exe 运行
```

`publish.ps1` 会做五件事：publish C# 后端 → 拷贝前端 → 拷贝 Electron 运行时 → 裁剪语言包与冗余文件 → 校验产物形状。最后一步还会调用 `docs\sanitize-artifact.ps1`，删掉运行残留并逐个比对 6 个代码文件与仓库的 md5，不一致直接判定构建失败（宁可不出包，也不发一份陈旧产物）。

最后一步是硬性自检：必需文件（.NET 运行时、Electron 引擎、`resources\default_app.asar` 等）缺失，或自包含产物体积明显不对，脚本直接失败退出。目的只有一个——**`产物` 目录里的东西必须和 Release 包里的东西一致**，发布用的就是这份目录压出来的包，不允许出现「本机能跑、别人下回去起不来」。

**在 Linux 上交叉打包**（不需要 Windows 机器，产物与默认 `publish.ps1` 等价）：

```bash
scripts/pack-linux.sh                # 产物在 .build/GameFPS/
scripts/pack-linux.sh --to-share     # 顺带同步到共享目录 /mnt/hgfs/fps/GameFPS
```

它用 `dotnet publish -r win-x64 --self-contained` 交叉编译后端，再从 npmmirror 拉取
win32-x64 的 Electron 运行时（首次约 120 MB，缓存在 `~/.cache/gamefps-pack/`），
按同样的规则裁剪语言包与无用 DLL。包内 `版本.txt` 记录 tag、commit 与构建时间。

## 三、技术原理

### 1. 帧率从哪来（核心）

`Microsoft-Windows-DxgKrnl` 是内核态图形 provider。无论游戏用 D3D9 / D3D11 / D3D12 / Vulkan，
每一帧的 Present 最终都要经过 `dxgkrnl.sys`，在那里产生：

| 项 | 值 |
|---|---|
| Provider GUID | `802ec45a-1e99-4b83-9920-87c98277ba9d` |
| 事件 ID | **184**（task = Present） |
| 关键字掩码 | `0x08000000`（Present） |

我们订阅这个 provider，从**事件头**里直接读到发起进程 PID 与高精度时间戳，
得到逐帧时间线，再算出 FPS / 帧时间 / 1% Low。

> 实测依据：某 240 FPS 的 WebGL 负载下，相邻事件间隔稳定为 4.17 ms，
> 与"240 帧/秒"完全吻合，三条独立指标（帧时间、FPS、累计帧数增速）互相印证。

注意：`0x08000000` 这个关键字过滤非常关键——不过滤时 DxgKrnl 每秒会产生约 6 万条
无关事件；过滤后只剩 Present。

### 2. 为什么必须管理员权限

创建 ETW 会话需要 `SeSystemProfilePrivilege`，因此 `GameFPS.exe` 的清单里设了
`requireAdministrator`，双击时会弹一次 UAC。

### 3. ETW 残留会话陷阱（重要）

ETW 的 **realtime 会话在宿主进程被强制终止（taskkill / 任务管理器结束）时不会自动回收**，
会作为孤儿会话一直占用系统资源。残留累积到一定程度后，`StartTrace` 就开始返回
`ERROR_NO_SYSTEM_RESOURCES (0x800705AA)`，表现就是"程序打不开、弹系统资源不足"。

程序已做处理：使用**固定会话名** `GameFPSMonitor`，每次启动前先 `logman` 清掉同前缀的残留会话。
正常通过托盘"退出"关闭则不会有残留。

### 4. 悬浮窗

用 `UpdateLayeredWindow` 推送 **预乘 Alpha** 的 32 位位图（普通 `TransparencyKey` 方案做不到半透明），
窗口带 `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TOPMOST`，
实现半透明、点击穿透、不抢焦点、始终置顶。

### 4.1 屏幕准星

> **来源说明**
>
> 准星功能的**参数设计、样式定义与交互流程参考 [NexBox](https://github.com/MuLiuSaMa/NexBox)**
> （Tauri + Rust + React 实现，仓库未提供 LICENSE 文件）。本项目用 **C# + WinForms 重新实现**，
> 与仓库原有架构保持一致 —— 搬过来的是「功能」（参数集合、几何形状、交互流程），
> 不是代码。得益于两侧语言、框架与进程模型完全不同，本仓库中**没有一行准星代码来自该项目**。
>
> **7 张内置预设图**（`cat` / `donk` / `s1mple` / `ropz` / `MMW2.0` / `SSCJ` / `TShape`）
> **直接取自该项目**，原样保留，仅随功能一起分发。由于上游没有 LICENSE，
> 这组图片的版权归原作者所有；如果你是原作者并希望移除，开个 issue 即可。
>
> 以下部分均为**独立实现**，与参考项目无关：几何绘制的具体坐标计算、
> `UpdateLayeredWindow` 预乘 Alpha 推送、按住检测的轮询方案、
> 预设的 `localStorage` 存储、图片落盘与回读、以及全部前端代码。

准星和悬浮窗是同一套机制的两个应用，都是 C# 侧的分层窗口（`CrosshairForm.cs` / `OverlayForm.cs`），
同样用 `UpdateLayeredWindow` 推**预乘 Alpha** 位图，所以边缘是逐像素抗锯齿的，不是硬边。

和悬浮窗的差别只有两点：

1. **窗口尺寸等于准星自身的包围盒**（不是整块面板），位置 = 目标显示器中心 + 偏移量；
2. **`WS_EX_TRANSPARENT` 常开** —— 准星永远不吃鼠标事件，游戏里的点击照常穿透，
   也不需要在游戏内切焦点，因此不引入任何输入延迟。

绘制几何与前端预览（Canvas）一一对应：十字四臂从 `Gap` 处向外延伸 `Size`，
圆环半径 / 方框半边长为 `Size`，中心点直径为 `DotSize`，描边则是在同一几何上
用 `Thickness + OutlineThickness * 2` 的笔宽先画一遍深色垫底。

**两种渲染方式**（`RenderMode`）：

| 方式 | 画什么 | 关键参数 |
|---|---|---|
| 程序绘制 | 用几何参数实时画矢量准星，任何 DPI 都锐利 | 样式 / 大小 / 粗细 / 留空 / 中心点 / 颜色 / 描边 |
| 图片绘制 | 内置 7 张预设图任选，或上传自己的图片 | 图片 + 图片尺寸 |

图片准星的处理和原版一致：**直接拉成正方形**（不保持宽高比），窗口边长
`max(图片尺寸 + 16, 64)`；不透明度通过 `ColorMatrix` 的 alpha 通道一次性乘进图片，
不再逐像素处理。前端选中的图片会以 base64 交给后端，由后端写进
`%LOCALAPPDATA%\GameFPSMonitor\crosshair\`（只取文件名，挡掉路径穿越），
**所以关掉界面、甚至杀掉 Electron 进程，准星照样在**。图片解码失败时自动回退到程序绘制，
不会留一个空白窗口。

**按住显示**（`CrosshairHold.cs`）：启用后准星只在按住指定键时出现。
实现用 16 ms 轮询 `GetAsyncKeyState` 读按键状态位，**没有装低层键鼠钩子** ——
`WH_MOUSE_LL` / `WH_KEYBOARD_LL` 会给每一次输入都插同步回调，既加延迟又容易撞反作弊，
而轮询只读状态、最坏 16 ms 延迟，且完全不影响输入链路。支持 `Mouse1`–`Mouse5`
（左/右/中/侧键）、`A`–`Z`、`0`–`9`、`F1`–`F24`。

**我的预设**存在 `localStorage` 的 `gfps.cxPresets`，一条预设就是一份完整参数快照
（样式、尺寸、颜色、描边、图片路径、按住设置），换机不跟走，符合"本机兜底"的定位。

> 和悬浮窗一样，**独占全屏**下同样盖不上去（见「七、已知限制」第 1 条），
> 游戏改成无边框全屏即可。

### 6. 监测目标：自动检测 vs 手动指定

默认走**自动检测**：优先取前台窗口对应的渲染进程，否则取帧率最高的活跃进程。
大多数情况够用，但有副作用——alt-tab 切到浏览器、或者 Wallpaper Engine 这类常驻渲染的
进程，都可能被短暂当成"游戏"，把记录切碎。

所以在**实时监控页顶部**的「监测目标」下拉框里可以手动指定：

- 下拉列表只列出**当前正在渲染**的进程（有 Present 活动），并显示各自的实时帧率
- 选中后**钉住那个具体 PID**，不再跟随前台窗口切换
- 该进程重启换了 PID 也没关系：只要进程名不变，会按名字在"正在渲染的进程"里重新接上
- 选回第一项「自动检测」即可恢复自动模式
- 改了**立即生效**，不用点保存

> **一个容易踩的坑**：按进程名找 PID 时，必须优先在"有 Present 活动的进程"里找。
> Edge / Chrome / Electron 这类应用会有十几个同名进程（浏览器进程、GPU 进程、渲染进程、
> utility…），直接取 `GetProcessesByName` 的第一个很可能拿到一个根本不提交帧的进程，
> 表现就是"锁定了但 FPS 一直是 0"。所以界面传的是具体 PID，后端也只在渲染进程里按名字兜底。

## 四、游戏记录：退出游戏时自动保存

每场游戏结束时会自动把本场帧率落盘，不需要手动操作。

**触发条件**：**游戏进程彻底退出**。

切到桌面、加载场景、暂停、最小化都不算结束——一整局游戏会记成一条完整记录。
如果担心"进程没退但再也不渲染"的异常情况，可以在设置里给「空闲兜底超时」填一个秒数（默认 0 = 关闭）。

**保存位置与内容**：

所有数据都放在 **`%LOCALAPPDATA%\GameFPSMonitor\`**，**不在程序目录里**——这样覆盖更新软件时历史记录不会丢。

| 文件 | 内容 |
|---|---|
| `%LOCALAPPDATA%\GameFPSMonitor\settings.json` | 全部设置 |
| `%LOCALAPPDATA%\GameFPSMonitor\records\sessions.json` | 每场一条汇总（最新在前），界面的「历史记录」页直接读它 |
| `%LOCALAPPDATA%\GameFPSMonitor\records\csv\<时间>_<游戏名>_pid<N>.csv` | 逐帧帧时间与瞬时 FPS，可用 Excel 打开做同口径分析 |

> 从 v1.0.3 及更早版本升级时，程序首次启动会自动把旧位置（程序目录）里的
> `settings.json` 和 `records\` 搬到新位置，历史记录无需手动迁移。

**汇总字段**：开始/结束时间、时长、总帧数、参与统计帧数、平均 FPS、中位 FPS、最高/最低 FPS、
平均/最小/最大帧时间、**1% Low**、**0.1% Low**、卡顿帧数（帧时间 > 平均值两倍）、逐帧 CSV 文件名。

> **与实时数值的区别**：实时监控页上的 1% Low 是最近约 34 秒滑动窗口的值；
> 而记录里的 1% Low 覆盖**整场**，更能反映这一局真实的长尾卡顿。
> 这也是为什么要专门累积整场样本，而不是直接存快照。

**在界面里查看**：「历史记录」页顶部是**对比曲线图**（最近 20 场的平均 FPS / 1% Low / 0.1% Low 三条线），
下方是每场的卡片；点卡片会展开该场的完整字段和**逐帧帧率曲线**（从 CSV 读回、自动降采样到 4000 点）。
右上角可「刷新」或「打开记录文件夹」。游戏结束时托盘也会弹一条提示。

**设置**（设置页 → 游戏记录）：关闭自动记录、是否写逐帧 CSV、
无渲染多久算本场结束、历史最多保留多少条。

**已知噪音**：任何持续在屏幕上渲染的进程都可能被当成"游戏"记一场，例如
Wallpaper Engine 动态壁纸（`wallpaper32`）、WebView2 组件（`msedgewebview2`）。
这类记录通常帧数很少，可以忽略；不想要的话可以在设置里关掉自动记录。

## 七、已知限制

1. **独占全屏（exclusive fullscreen）游戏上悬浮窗无法显示。**
   这是所有非注入方案的固有边界——独占全屏会绕过桌面合成器，任何普通窗口都盖不上去。
   游戏加加/RTSS 是靠**注入游戏进程**解决的，那属于我们刻意避开的路线。
   实践上影响不大：Win10 1803+ 的"全屏优化"让绝大多数游戏实际以无边框全屏运行，
   悬浮窗可以正常显示。若遇到不显示的，把游戏改成"无边框窗口"即可。

2. **同一 PID 的多个交换链会被合并计数。**
   例如浏览器多个窗口共用同一个 GPU 进程时，帧数会叠加。
   单个游戏进程通常不受影响。

3. **独占全屏 + HDR / 受保护内容**可能不产生 Present 事件。

4. 温度、功耗、风扇转速需要加载内核传感器驱动（游戏加加用的是 PawnIO），
   本工具**刻意不装驱动**，因此不提供这些数据。

## 八、排错

| 现象 | 原因与处理 |
|---|---|
| 弹"系统资源不足 (0x800705AA)" | ETW 残留会话耗尽资源。以管理员运行 `logman query -ets`，把 `GameFPSMonitor*` 逐个 `logman stop <名> -ets`；新版启动时会自动清理 |
| 弹"帧率采集需要管理员权限" | 从非提权环境启动。右键 → 以管理员身份运行 |
| 悬浮窗不显示 | 游戏是独占全屏（见限制 1）；或按 `F9` 切换；或检查设置里"仅在检测到游戏时显示" |
| 主界面显示"未连接" | 后端未运行，或 8731-8750 端口全被占用 |
| 主界面打不开 / 白屏 | 看 `app\electron.log`，里面有主进程的分步日志 |
| 数值一直是 `--` | 没有进程在渲染，或当前前台窗口不是游戏 |
| 玩完游戏后历史记录是空的 | 检查设置里是否关掉了"自动保存帧率记录"；看 `session-debug.log` 里的会话起止与结算原因 |
| 历史里出现奇怪的进程（如 wallpaper32） | 那是常驻渲染的壁纸/组件，属于正常噪音，可忽略或关掉自动记录；也可以用「手动指定进程」锁定到目标游戏 |
| 锁定了进程但 FPS 一直是 `--` | 该进程当前没在渲染（比如游戏被最小化、或浏览器切到后台）。让它回到前台或重新启动即可 |
