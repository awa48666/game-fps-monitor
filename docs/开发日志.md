## 总览与阅读方式

### v1.0.0 ｜ 2026-10-18 22:09 ｜ commit `0e48abc`（`60cd7e1` 为同日补充的 Releases 下载入口与构建说明）

- **需求/问题**：初始提交 message 原话——「基于 ETW (DxgKrnl Present 事件) 的无注入帧率采集，Electron 前端 + C# 后端」，技术要点写明「帧采集走 Microsoft-Windows-DxgKrnl 的 event id 184，需要管理员权限」「CPU 功耗取自 Intel RAPL 的 Energy Meter 计数器，无需内核驱动」「大小核通过 GetLogicalProcessorInformationEx 的 EfficiencyClass 区分」「GPU 频率/功耗/温度走 NVML，仅 NVIDIA 可用」。一次提交 35 个文件、6621 行。

- **修了什么**：立起整条链路——游戏内点击穿透悬浮窗（FPS / 帧时间 / 1% Low / 0.1% Low / CPU / GPU / 显存 / 内存）、主界面曲线与历史记录、逐帧 CSV 回放、全局热键、设置热更新、进程彻底退出时自动存档。

- **怎么修的**：
  - **帧源**：`EtwFrameCapture.cs:33` 硬编码 DxgKrnl provider GUID `802ec45a-1e99-4b83-9920-87c98277ba9d`；`:69` `EnableProvider(DxgKrnlProvider, TraceEventLevel.Verbose, PresentKeyword)`，`PresentKeyword = 0x08000000UL`（`:26`，注释「只放行 Present 相关事件，避免每秒 6 万条噪声」）；`:154-161` 回调里再过一道 `(int)e.ID != PresentEventId` 的精确匹配（`PresentEventId = 184`，`:23`），只取 `e.ProcessID` 与 `e.TimeStampRelativeMSec` 两个字段，全进程只有这一条数据入口。
  - **会话回收**：`:31` 会话名固定为 `GameFPSMonitor`（不掺 PID），`:63` 建会话前先 `CleanupStaleSessions()`（`:95-136`，起 `logman.exe query -ets` 找同名残留再逐个 `logman stop ... -ets`）。原因是 realtime 会话在宿主进程被强杀时不会自动回收，攒够了 `StartTrace` 就返回 `ERROR_NO_SYSTEM_RESOURCES (0x800705AA)`，表现为「重装后再也采不到帧」。
  - **提权**：`app.manifest:5-11` `level="requireAdministrator"`，注释直指「创建 ETW 内核会话(SeSystemProfilePrivilege)，必须提权」；`EtwFrameCapture.cs:18` 与 `:43`（`IsElevated`）配套。
  - **探针**：`backend/EtwProbe/Program.cs` 是脱离界面跑真实引擎的控制台验证器——`:19-25` 先打印是否提权并警告「未提权，ETW 会话必然失败」，`:31-35` 直接 `MonitorEngine.Start()` 并透出 `StartError`，`:37-52` 每秒打一行 `FPS / 1%Low / 0.1%Low / 帧时间 / 总帧 / CPU / GPU / 显存 / 内存`，`:54-60` 结束时打最近 12 帧的逐帧帧时间。event 184 是否「每帧一次」、keyword 过滤后事件速率是否吃得消，都是先用它实测确认的，`:22` 注释「已实测验证」即来源于此。
  - **滑动窗口与 Low 值**：`FrameStats.cs:15` 维护最近 1 秒时间戳队列（`:44-46` 入队后把超过 1000ms 的队头弹出），`:13` 另开 2048 容量的环形帧时间数组（`:36-38` 头指针取模推进）。`:69` FPS 直接取队列长度——窗口就是 1 秒，帧数即 FPS。`:110-119` `SlowestPercentFps`：升序排序后取最慢 `ceil(n·p)` 个求平均，再 `1000/avg`，`p` 分别为 0.01 / 0.001（`:85-86`），即 1% Low / 0.1% Low 的标准算法。`:30-40` 只接受 `0 < dt < 2000` 的间隔，切场景与暂停不进分布。
  - **整场统计**：`GameSession.cs:13` 上限 2,000,000 帧（float 约 8 MB），`:16-21` `MinPlausibleFrameMs = 0.2` 专门丢弃 ETW 对同一帧重复上报产生的 0.1ms 级伪间隔（会算出 7000+ FPS 污染「最高 FPS」），`:24` 超过 2000ms 视为切场景。
  - **悬浮窗渲染**：`OverlayForm.cs:117-127` `CreateParams` 设 `WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TOPMOST`，非拖动模式再加 `WS_EX_TRANSPARENT`（`:134-148` `SetDragMode` 临时摘掉它，否则收不到鼠标消息没法拖位置）；`:955-1024` `PushToScreen` 用 `CreateDIBSection` 建 32bpp 顶层 DIB（`:961-974`，`biHeight` 取负 = 自上而下），`:978-1000` 逐像素 `d[c] = s[c]*a/255` 手工把 GDI+ 的非预乘像素乘上 alpha，`:1005-1013` 以 `AC_SRC_OVER + AC_SRC_ALPHA + ULW_ALPHA`（常量在 `:37-39`）一次 `UpdateLayeredWindow` 推屏。
  - **节拍与进程编排**：`MonitorEngine.cs:99` `TickIntervalMs = 200`、`:212` 定时器；`IpcServer.cs:32-38` 从 8731 起最多顺延 20 个端口；`AppHost.cs:722` 以 `"{appDir}" --ws-port={port} --no-sandbox` 拉起 Electron，`:727-731` 清掉继承来的 `ELECTRON_RUN_AS_NODE`；`Program.cs` 用全局 Mutex 做单实例。

- **为什么这样修**：
  - 选 DxgKrnl event 184 是因为 D3D9/11/12、Vulkan 的 Present 最终都要落到 `dxgkrnl.sys`（`:12-16` 注释），这是「不往游戏进程里注入一行代码」就能拿到逐帧时间线的唯一公共必经点，同时事件头自带 PID 与高精度时间戳。
  - keyword `0x08000000` 是必须的一层：不过滤的话托管侧 pump 线程每秒要接约 6 万条内核图形事件，帧数据反而被噪声挤掉；先用 `EtwProbe` 数过事件量才敢定这个掩码。
  - 管理员权限不是「更稳妥」而是硬要求——`SeSystemProfilePrivilege` 只给提权进程，普通令牌下建会话直接抛异常。
  - 分层窗口 + 预乘 alpha 是悬浮窗外观的唯一解：`TransparencyKey` 只能做「全透明 / 不透明」二值，拿不到半透明圆角面板，文字抗锯齿也会在键控色边缘糊掉（`:15-16` 注释）。代价也如实写进 `:18-20`：非注入层只能盖在窗口化 / 无边框全屏上，真正独占全屏的游戏独占显示输出，这条路盖不住（RTSS、游戏加加靠注入解决）。
  - **早期 CPU 占用的坑就在这一版埋下**：`HardwareMonitor.cs` @`0e48abc` 的 `:90-94` 注释断言「用 % Processor Time 而不是 % Processor Utility……后者在睿频/大小核上明显虚高（实测 i5-13500HX 跑到 108~115%，真实占用只有 68%），% Processor Time 是传统时间占比口径，与任务管理器、WMI 一致」。后半句是错的：任务管理器与 Process Lasso 都是 Utility 口径，Time 才是那个跟用户习惯数字对不上的（同秒整机 7% vs 28%）。这条一直到 v1.0.21（`6041f75`，改 `HardwareMonitor.cs:88-106`）才翻转成 Utility 并删掉该注释。同一版还留下小核基准 = 全核最大 `Processor Frequency` × 0.72 的经验换算（现 `HardwareMonitor.cs:244-248`），以及大小核频率靠 `% Processor Performance` 推算的做法（v1.0.11 改掉，见下文）。

## 第五阶段：现场取证与基础设施修路（v1.0.28 ~ v1.0.29）

### v1.0.28 ｜ 2026-10-27 ｜ commit `bd795df`

- **需求/问题**：宿主机任务管理器里 Electron renderer 进程内存一度涨到 **1813 MB**；运行 22.9 小时后在系统 commit 压力下自行回落到 295 MB，随后仍以约 **78 MB/h** 缓爬。没有稳定复现路径，只能靠现场数据判断是不是泄漏。
- **修了什么**：新增纯诊断采样，不改任何用户可见行为。
- **怎么修的**：`app/main.js:160` 在应用就绪时调用 `startMemorySampling()`；`:168` 定义该函数，每 5 分钟把 `app.getAppMetrics()`（`:174`）返回的各进程 working set / heap / CPU 与窗口状态（visible / minimized / hidden）写入 `electron.log`（该日志路径定义在 `main.js:10`，超 256 KB 重开）；启动时立即采一条用于核对格式。
- **为什么这样修**：先排除「是不是 JS 堆泄漏」。已在本地 Linux 跑过三组对照实验——`visible + 软渲染 12min`、`hidden + 软渲染 30min`、`visible + SwiftShader 30min`——`heapUsed` 全程 5-10 MB 平稳、DOM 节点数恒定、无失控动画与累积数组；`visible` 组 RSS 有约 +160 MB 的合成器固定成本但 2 分钟即平台化。静态审查 `app.js` 全部 `push`/监听器/画布路径无泄漏形态，后端 `snapshot` 数组都有上限（240 / 180 点）。结论是**非 JS 堆泄漏**，而是 Chromium 的「高水位 + 惰性归还」行为。剩下未控的变量只有 Windows 硬加速合成路径、150% DPI、以及真实窗口状态；而 SSH 会话因窗口站隔离取不到窗口状态，只能让宿主机自己记录——所以采样必须落在宿主机能读到的日志里。
